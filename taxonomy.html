How skill IDs map to the taxonomy

Every skill belongs to exactly one category, and its ID embeds the category and subcategory:

yc-{category}-{subcategory}-{descriptor}
Skill ID (illustrative) Category Subcategory Descriptor
yc-fundraising-seed-round-timing fundraising seed-round timing
yc-hiring-first-technical-hire hiring first-hires technical-hire
yc-product-mvp-no-code-approach product mvp no-code-approach

The IDs above are illustrative examples from the project docs — no skill files are published yet.

IDs are lowercase, hyphen-separated, and at most 6 words after yc-{category}. The category in the ID must match the skills/{category}/ directory and the file's frontmatter.

Tags cross the boundaries

Categories are exclusive, but tags are not. A skill can carry up to 10 lowercase tags from any topic, so a fundraising skill can surface under %hiring. Consumers filter with /category and %tag prefixes; the pre-computed similarity matrix links related skills across categories.

Why the taxonomy is locked

  • Prevents overlap: without clear boundaries, "pricing strategy" could land in growth, strategy, or product.
  • Enables reliable routing: agents using the /category filter depend on a stable, known set of categories.
  • Prevents sprawl: a fixed set keeps the focus on core startup advice.
  • Maintains quality: each category should have substantial YC content behind it.

New categories are possible but require a pull request — they can't be added silently. The single source of truth is config/taxonomy.yml in the repository.
